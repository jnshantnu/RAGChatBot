01

Ingestion pipeline

Offline. Runs on demand via python -m ingest.ingest; idempotent — a document's content_hash (raw file bytes) is checked against the registry before anything is re-embedded.

02

Query pipeline

Live, per request. Two off-ramps leave the main line: a permission refusal decided from intent + role alone, before the corpus is ever touched, and an abstain decided from retrieval confidence, before the LLM is ever called.

03

Retriever internals

One chunks table, two index arms, one round trip each. The permission filter runs as a predicate inside both index scans, not as a step afterward.

tsv & embedding — parallel, not sequential

db/schema.sql

tsv tsvector GENERATED ALWAYS AS (to_tsvector('english', chunk_text)) STORED embedding vector(1536)

Both are derived straight from chunk_text, independently — neither reads the other. tsv is a generated column: Postgres computes it itself, instantly, the moment a row is written, no application code involved. embedding is the opposite kind of work: ingest/embed.py sends the text to an external model over the network and gets a 1536-number vector back, before the row is even inserted. One is free and automatic; the other is a paid API call — that asymmetry is why ingestion batches embedding calls (§01) but never has to think about tsv at all.

ACL predicate

retrieval/hybrid_search.py

WHERE acl && :user_groups AND index_version = 1

Applied identically on both arms. A restricted chunk cannot enter the candidate set for a session lacking the matching group — enforced before ranking, not after.

RRF fusion

retrieval/rrf.py

score(d) = Σ 1 / (60 + rank_arm(d))

Fuses on rank, not raw score — cosine distance and ts_rank_cd live on incomparable scales, so rank is the only fair currency between them. Over-fetch: 50 rows/arm.

Keyword arm, corrected

retrieval/hybrid_search.py

plainto_tsquery → 'a' & 'b' & 'c' rewritten to 'a' | 'b' | 'c'

Postgres's default ANDs every query term, so one off-corpus word ("work" in "how does the downgrade policy work") zeroed an otherwise perfect match. Rewritten to OR; ts_rank_cd still rewards fuller overlap.

04

What broke the confidence gate — three times

The case study's gate reads post-rerank scores. This POC didn't have one at first (§02 marked it TODO), which forced the gate onto weaker signals — and each one broke in its own way as the system evolved.

Round 1 — RRF rank is not a confidence signal

pgvector's HNSW arm always returns its k nearest neighbours, relevant or not — an on-topic query and an off-topic one produce the same rank-1…50 shape, just anchored at different absolute similarities. Gating on the fused rank score alone abstained on real answers and answered on nonsense with equal confidence.

Interim fix: gate on raw cosine similarity instead (bounded, comparable across queries) — worked against the OpenAI embedding model on the original synthetic corpus.

Round 2 — raw similarity doesn't transfer across embedding models

Switching to Qwen3-Embedding-8B for the real corpus broke the "fixed" gate immediately: an off-corpus query ("Can I integrate with Salesforce?") scored a higher cosine similarity than a genuinely relevant match on the corpus at the time — both shared generic API vocabulary, which is all a bi-encoder's angle-comparison can see. No threshold separated the two classes on this model.

Real fix: build the cross-encoder rerank step (§02) and point the gate at its calibrated 0-1 relevance score instead. Raw similarity is now only a documented degraded.rerank fallback.

QueryRerank scoreGate verdictFinal answer
“How do I authenticate to the Partner WebServices API?”0.999continuescorrect, cited
“Does the API support GraphQL?”0.002abstains“I don't have that” (no LLM call)

Live numbers, reproducible via retrieval.cli_test — not fixed constants; they shift whenever chunk text changes (see the Salesforce row below).

A later fix moved that Salesforce score — on purpose, with a trade-off

After §05's doc-title prefix was added, the Salesforce query's gate score rose from 0.10 to 0.46 — high enough to now pass the gate — because the prefixed title text made the whole "Place Order API" document read as more generally API/integration-relevant, the same effect that correctly fixed §05's bug. The query still gets the right final answer, but now via the LLM's grounding refusal (the second defense layer) rather than the gate catching it outright. A concrete, measured example of the recall/precision trade-off eval loops exist to catch — eval/run_eval.py only checks the gate layer, so this kind of shift is exactly what its "note" at the bottom is warning you to check by hand.

Round 3 — vague phrasing under-scores a genuinely correct match

Two real user questions retrieved the exactly right chunk at rank 1, yet scored too low to pass the 0.30 bar: "which APIs are available to me?" (0.2330, correct chunk in buysell-pws-place-order-api-implementation-guide) and "which business model is applicable to me? I am in Indonesia" (0.0311, correct grounding entirely in the internal ADSK-BIZ-RULES.md). The cross-encoder reads conversational, generic phrasing as less confident than technical phrasing, even when it found the right answer. A genuinely unanswerable query ("Does the API support GraphQL?") scored 0.0017 by comparison — nowhere near either real case.

Fix, in two parts: lowered MIN_RERANK_SCORE 0.30 → 0.20 (rescues the first case; verified safe against both known-correct abstains). Added a dominance rescue below even that: a result clearing a low floor (0.01) and beating the runner-up by 10x or more is trusted regardless of absolute score — a real match buried by vague phrasing still stands out sharply from the noise around it (Indonesia: 0.0311 vs. 0.0001 runner-up, ~300x), while genuine noise stays clustered close together (GraphQL: 0.0017 vs. 0.0004, ~4x). Both new queries are permanent regression cases in eval/golden_set.json.

05

A chunk can't be found for identity it never states

A different failure class from §04 — this one's the case study's own "chunking failure" category, generalized from a chunk boundary to a document boundary.

"which apis are available for buy sell model" → abstained (wrongly)

Retrieval found the exact right page at rank 1 — but reranked it 0.03 (abstain). Reading the actual chunk text explained why: the word "BuySell" never appears anywhere in that PDF, not on the page, not even on the title page. It's a filename-only distinction (BuySell-pws-place-order-api-implementation-guide.pdf vs. an NxM- counterpart covering the other business model) — invisible to embedding, keyword index, and reranker alike, none of which ever see filenames.

Fix: prefix every chunk with a filename-derived title ([BuySell PWS Place Order API Implementation Guide]) before it's embedded, indexed, or reranked — "contextual retrieval." The fix had to come from the filename specifically, since the document's own content doesn't state its business model either. Score went from 0.03 → 0.55 on re-ingestion. Kept as a permanent case in eval/golden_set.json.

06

A layer with no equivalent in the case study: hidden operating guidance

Some content needs to shape an answer's content without ever being citable or visible — business rules the system operates by, not knowledge it shows sources for. ADSK-BIZ-RULES.md (5 chunks) is tagged internal: true and is the first real case of this.

Embedded and retrieved normally

ingest/chunker.py

An internal doc competes in the same hybrid search + rerank pipeline as everything else — it can win top rank (0.99+ scores measured) when genuinely relevant. Hiding it isn't a retrieval-time filter; it's a generation-time and API-time wall.

Two prompt blocks, one numbered

llm/generate.py

Citable chunks get [1]-style numbers the model can cite. Internal chunks go in a separate, unnumbered "Internal operating guidance" block the model is told to use but never reveal, quote, or cite — there's no bracket number to leak.

Stripped before it leaves the server

chat.py

Every score/debug field is filtered by is_internal before the API response is built — not just the citation list. A non-revealing internal_guidance_used boolean is the only trace exposed, confirming it fired without saying what it said.

First version leaked nothing — by refusing to answer at all

The initial system prompt said "answer ONLY using the numbered context chunks." The model took that literally: asked "why doesn't Buy Sell have quote APIs" — a fact that exists only in the internal guidance — it replied "I don't have that information," even with the correct answer sitting in its own context. The instruction to stay silent about internal guidance had accidentally also made it unusable as a source.

Fixed by explicitly stating internal guidance is a valid, never-cited basis for a claim. Same question then answered correctly, with zero citations and zero exposure.

07

ACL enforcement, upgraded from narrative to real

Per ADSK-BIZ-RULES.md: only Distributors can place orders to Autodesk in the Buy-Sell model — Resellers cannot. That's now enforced at the SQL predicate, not just mentioned in prose.

Document-level ACL boundary

ingest/ingest.py

GetMyPrice manual, PlaceOrderV2 manual → acl: [role:distributor] 122 chunks, 2 docs

These two manuals are entirely dedicated to the restricted APIs. The general implementation guide (mixed content covering all 5 Buy-Sell APIs) stays public — page-level chunking can't cleanly split API-specific access within a shared overview page.

Pre-retrieval refusal, same shape as commission

chat.py: PERMISSION_RULES

Asking about PlaceOrderV2/GetMyPrice as a reseller is refused before retrieval runs at all — identical pattern to the principal-only commission rule, now with two independent entries instead of one.

"Available to me" means actually available

llm/generate.py: SYSTEM_PROMPT

A reseller asking "what APIs are available to me" now gets a list containing only what they can use — restricted items are omitted entirely, not listed-then-caveated.

Found while testing: refusal text was hardcoded to the wrong rule

The first version's refusal message always said "restricted to principal-level users" — copy-pasted boilerplate, regardless of which PERMISSION_RULES entry actually matched. A reseller asking about PlaceOrderV2 got told it was a principal restriction, which is simply false. Fixed by adding a restriction_label per rule instead of one hardcoded string.

08

Eval loop

18-query golden set against the real corpus (13 answerable + 1 internal-only, 4 deliberately not) run via python -m eval.run_eval. Two-layer defense against the unanswerable ones: the fast retrieval gate catches clear misses before an LLM call; the LLM's own grounding instruction catches the subtler content gaps the gate lets through.
